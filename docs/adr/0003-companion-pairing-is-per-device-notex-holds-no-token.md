# Companion pairing is per-device; Notex holds no token to the user's machine

Designing the local companion's API (TBR-56), we chose to store the companion's `{ baseUrl, token, checkoutId }` in the browser's `localStorage` keyed by `repositoryId`, rather than on the `repositories` row in D1. The alternative (server-side pairing state) was rejected on two grounds: it would make Notex the custodian of a credential to a machine it cannot see or verify, contradicting the founding constraint of TBR-53 that execution and secrets stay local; and because a companion is scoped to one checkout on one machine, a shared row would show every teammate a connection they never made and cannot use. This means pairing is per-browser-profile — the same user re-pairs on a second machine, which is correct, because it *is* a different machine — and it means the checkout↔Repository binding is confirmed by a human at pair time and guarded thereafter by a client-side `checkoutId` comparison rather than by a schema change. No column is added to `repositories`; `companionCheckoutId` was rejected specifically because per-machine state does not belong on a shared row. See `docs/specs/companion-api.md` §3.
