# The Local Network Access prompt fires only from an explicit Connect flow

Deciding the companion's browser contract (TBR-56, consuming TBR-54's research), we chose to trigger the Local Network Access permission prompt exclusively from a dedicated "Connect companion" flow in Repository settings — after a screen that shows the user the browser's own wording ("…wants to look for and connect to any device on your local network") and states that we only talk to `127.0.0.1` on this machine.

> **Updated by TBR-139 (hub/satellite switching).** The original wording named a single fixed port, `127.0.0.1:7717`. Once a checkout switch hands the browser a different companion process's own port (TBR-135's direct handoff), that's no longer literally true — the browser talks to `127.0.0.1:7717` (the hub) and then, after switching, to `127.0.0.1:<the switched-to checkout's own port>`. The permission itself doesn't change: `loopback-network` is granted per-origin, not per-port, so no second prompt fires. Only the disclosure copy needed correcting, in both this ADR and the explainer text in `graph-gui.md` §5.2 — see TBR-139 for the corrected wording. The alternative (letting the prompt fire implicitly on first graph use, from a Question's "draft this Answer from the graph" action) was rejected because a denial is a persisted per-origin Block that is not self-healing: recovery is buried in site settings and, in practice, means telling users to clear browsing data for the site — the support path Dell, Duo, Twingate and others now publish KBs for. One shot at a moment the user is primed beats one shot mid-task. This means the Question-level graph action renders disabled-with-explainer until a connection exists, and it means the client resolves eight connection states (`unsupported`, `unpaired`, `needs-permission`, `blocked`, `unreachable`, `outdated`, `unauthorized`, `mismatched`, then `connected`) by calling `navigator.permissions.query({name: "loopback-network"})` *before* any fetch — because a denied permission and an absent companion are the same opaque `TypeError` at the `fetch()` layer, and only `blocked` warrants the site-settings recovery copy. See `docs/specs/companion-api.md` §6.
