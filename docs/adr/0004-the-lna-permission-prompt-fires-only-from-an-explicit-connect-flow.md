# The Local Network Access prompt fires only from an explicit Connect flow

Deciding the companion's browser contract (TBR-56, consuming TBR-54's research), we chose to trigger the Local Network Access permission prompt exclusively from a dedicated "Connect companion" flow in Repository settings — after a screen that shows the user the browser's own wording ("…wants to look for and connect to any device on your local network") and states that we only talk to `127.0.0.1:7717`. The alternative (letting the prompt fire implicitly on first graph use, from a Question's "draft this Answer from the graph" action) was rejected because a denial is a persisted per-origin Block that is not self-healing: recovery is buried in site settings and, in practice, means telling users to clear browsing data for the site — the support path Dell, Duo, Twingate and others now publish KBs for. One shot at a moment the user is primed beats one shot mid-task. This means the Question-level graph action renders disabled-with-explainer until a connection exists, and it means the client resolves eight connection states (`unsupported`, `unpaired`, `needs-permission`, `blocked`, `unreachable`, `outdated`, `unauthorized`, `mismatched`, then `connected`) by calling `navigator.permissions.query({name: "loopback-network"})` *before* any fetch — because a denied permission and an absent companion are the same opaque `TypeError` at the `fetch()` layer, and only `blocked` warrants the site-settings recovery copy. See `docs/specs/companion-api.md` §6.
