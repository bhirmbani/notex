# The Companion ships as a workspace package in the Notex repo, published to npm

Assembling the graph-companion spec (TBR-60, over TBR-53's map), we chose to ship the Companion as `packages/companion` in this repository — adding Bun workspaces, leaving the Notex app at the repo root — and to publish it to npm as `notex-companion` rather than developing it in a separate repository. The coupling that decided it is the op types: `docs/specs/companion-api.md` defines the five ops once as typed request/response pairs, `docs/specs/notex-mcp-server.md` §2.1 requires the MCP entry point to *import* those types rather than restate them, and the browser client needs the same types to speak to the same server — so a separate repository would put a publish-and-bump round trip in front of every spec refinement during v1, at exactly the point where the shape is still moving. Publishing is nonetheless in v1 scope and not deferred: the `unreachable` connection state tells the user to run `npx notex-companion`, which is the string every first-time user meets, and it is false until the package exists on the registry (the name was unclaimed as of 2026-08-16). We keep the app at the root rather than restructuring into `apps/notex` + `packages/companion`, because that move rewrites every path in `wrangler.jsonc`, `drizzle.config.ts`, `vite.config.ts`, `migrations/` and `src/` for no user-visible gain and collides with every in-flight branch; root-as-app with one nested package is mildly impure and completely boring, which is the right trade for a layout change. The consequences: the Companion's Node/CLI toolchain coexists with the app's Workers toolchain in one lockfile; version compatibility between the two deliverables is handled at runtime, not by the monorepo (`ping.apiVersion` plus the `outdated` connection state, `companion-api.md` §6); and extracting to a standalone repository later stays cheap, whereas splitting first and merging later would not be.
